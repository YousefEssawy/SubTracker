# Spec 11 — Finish the internationalisation (W10)

> **You cannot run shell commands in this environment.** Do not attempt `npm`, `git`, `firebase`, `tsc`, or any test runner — the attempt is auto-denied and aborts your run with no output. Write files only. The orchestrator runs all gates and reports results back to you.

## Context

**Resolves:** F12 — user-facing strings hardcoded in English across contexts, services, and one form validator, in a bilingual EN/AR app.

SubTracker ships English and Arabic, with full RTL handling: `src/i18n.js` flips `document.documentElement.dir` on language change, and components carry `rtl:` Tailwind modifiers. Translation coverage is genuinely complete for markup — 396 English keys against 402 Arabic (the delta is Arabic plural suffixes).

But several user-visible strings bypass `t()` entirely. An Arabic user sees English error text in three places:

1. **Context toasts** — every one of the five data contexts calls `toast.error("Failed to sync …")` with a literal string.
2. **Service errors** — services throw English sentences that pages surface verbatim through `getErrorMessage(err)`.
3. **`TransactionFormPage.validate()`** — hardcodes its messages, in a file that otherwise uses `t()` everywhere. `RecurrenceForm` does the same job correctly, which makes the inconsistency plain.

Plus one formatting bug: `BalanceCard` hardcodes `"en-US"` for number formatting, so Arabic users see Latin digits where the rest of the app uses locale-aware formatting.

**Spec 05 is the dependency.** It replaced service error sentences with a `ServiceError` class carrying a stable `code`. This spec maps those codes to translations. Read `src/utils/errors.ts` before starting to see what codes actually exist.

## Requirements

1. **Create `src/utils/errorMessages.ts`** exporting `translateError(err: unknown, fallbackKey: string, fallbackText: string): string`. It must:
   - when `err` is a `ServiceError`, look up `errors.<code>` in the active locale and return the translation
   - when that key is missing, fall back to the `ServiceError`'s English `message` — never render a raw key like `errors.space.nameRequired` to the user
   - when `err` is not a `ServiceError`, return `t(fallbackKey, fallbackText)`
   - use the `i18n.t` module import, not the hook, so it is callable from services-adjacent code and from tests

2. **Add an `errors` top-level section to both locale files**, keyed by the exact `ServiceError` codes spec 05 defined. Enumerate them from `src/services/*.ts` rather than guessing — **if a code exists in the services with no entry here, the user sees English**. List any code you could not find a natural Arabic phrasing for in your report rather than leaving English in the Arabic file.

3. **Every page that surfaces a service error uses `translateError`** in place of `getErrorMessage(err) || t(...)`. That is `TransactionFormPage`, `SpacesPage`, and `CategoriesPage` at minimum; grep for `getErrorMessage` and convert every call site that feeds a toast. `formatAuthErrorMessage` on the login/signup pages is **out of scope** — Firebase Auth codes are a separate namespace and those pages already fall back to `t("login.error")`.

4. **All five context toasts use `i18n.t`** with keys under a new `errors.sync` group, e.g. `errors.sync.spaces`. Import the `i18n` singleton as `src/utils/dateUtils.ts` and `src/utils/currencies.ts` already do — `import i18n from "@/i18n"` — rather than restructuring the contexts to use the hook.

5. **`TransactionFormPage.validate()` translates every message**, using keys under `finance.transactions` and matching `RecurrenceForm`'s naming: `spaceRequired`, `categoryRequired`, `amountInvalid`, `amountTooLarge`, `dateRequired`, `currencyRequired`. Keep the English text identical to today's so nothing changes for English users.

6. **`BalanceCard.fmt` uses the active locale**, matching `formatCurrency`'s pattern: `const locale = (i18n.language as string) || "en-US";`. Keep the existing `try/catch` fallback to `toFixed(2)`.

7. **`App.tsx`'s `"Loading..."` is translated** as `common.loading` with the English default `"Loading..."`.

8. **Every new key exists in both locale files, with the same nesting path**, in the same change. Arabic values must be real Arabic. Where a string interpolates, the Arabic keeps the same `{{placeholder}}` names.

9. **Create `scripts/check-locale-parity.js`** — a Node script comparing the two locale files' flattened key sets and printing keys present in one but not the other, exiting non-zero on a mismatch. It must:
   - treat i18next plural suffixes as equivalent: `days` in English satisfies `days_zero`/`days_one`/`days_two`/`days_few`/`days_many`/`days_other` in Arabic, and vice versa
   - print a clear summary (`N keys checked, M mismatches`)
   - **not** be wired into CI or `package.json` in this spec — it is a tool the operator runs

10. **No English string remains in a user-visible position** in the files listed under Scope. Empty states, aria-labels, placeholders, and toasts all count. Strings that are *not* user-visible — `console.error` messages, `throw new Error("useX must be used within XProvider")`, the `ServiceError` English fallback message — stay English.

## Conventions to follow

- **In components, use the hook:**
  ```tsx
  const { t } = useTranslation();
  ...
  {t("finance.transactions.amount", "Amount")}
  ```
- **Outside components, use the singleton:**
  ```ts
  import i18n from "@/i18n";
  const locale = (i18n.language as string) || "en-US";
  ```
- **Always pass an English default as the second argument.** Interpolation uses the object form:
  ```tsx
  t("finance.fileUpload.tooLarge", "File exceeds 5 MB limit ({{size}}).", { size: formatSize(f.size) })
  ```
- **Keys are nested by feature**, lowerCamelCase leaves, grouped under the existing top-level sections.
- **Plurals** use i18next suffixes, not manual branching — see `finance.spaces.spacesCount_one` / `_other`.
- **Do not change existing English text** while adding its key; an English-facing diff of zero is the goal outside the new `errors` section.
